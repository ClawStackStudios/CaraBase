## 2024-05-18 - [SQL Injection via Missing Type Sanitization in Schema Builder]
**Vulnerability:** Found a SQL injection vulnerability in the dynamic schema builder endpoint `systemApi.post('/tables')`. The code sanitized table names and column names using `safeIdent` (stripping non-alphanumeric chars), but directly interpolated the user-provided column type (`c.type`) into the `CREATE TABLE` query. This allowed attackers to craft payloads like `INT); DROP TABLE users; --` within the column type.
**Learning:** Even when developers remember to sanitize identifiers (tables, columns) in dynamic SQL, they often forget to sanitize metadata like data types. This is particularly dangerous in schema builder APIs where full table definition objects are passed from the client. The gap existed because `c.type` wasn't perceived as an identifier in the same way as a column name.
**Prevention:** Always validate and sanitize ALL parts of a dynamic SQL statement, including structural elements like column types. For data types, using a whitelist of allowed types (e.g., `['TEXT', 'INTEGER', 'REAL', 'BLOB']`) is even more secure than regex sanitization, though applying the same `safeIdent` (alphanumeric/underscore only) effectively mitigates injection in this specific context.

## 2026-10-01 - [Dangling SQLite WAL/SHM Journal Files on Backup Restoration]
**Vulnerability:** In `systemApi.post('/backups/import')` (and `src/server/routes/systemRouter.ts`), replacing the active database file (`carabase.sqlite`) after `db.close()` copied the uploaded backup directly over the main database file without unlinking lingering `carabase.sqlite-wal` and `carabase.sqlite-shm` files. In SQLite WAL mode, uncommitted or unflushed write-ahead log pages matching the database path remain on disk. When the process restarts and re-opens the database, SQLite attempts to replay the orphaned WAL file onto the new database file, causing database corruption (salt/page mismatch, malformed b-tree) or transaction contamination / state leakage (replaying old transactions onto the restored backup).
**Learning:** When hot-swapping or restoring a SQLite database running in WAL journal mode, the database file is not standalone. The WAL journal (`-wal`) and shared memory index (`-shm`) form a single atomic storage unit. Closing the DB handle does not guarantee that the `-wal` file is deleted or checkpointed if transactions were active or if the connection closed abruptly. Replacing the primary `.sqlite` file while leaving stale auxiliary journal files violates SQLite atomicity and journal integrity.
**Prevention:** Always match `/wipe` cleanup behavior when restoring or overwriting databases: immediately after calling `db.close()`, unlink both `activeDbPath + '-wal'` and `activeDbPath + '-shm'` if they exist, before copying or writing the replacement database file.
